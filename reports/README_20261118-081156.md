### 4.3 结论

1. **已排除存储与 PCIe**：`bi≈2`、`wa=0`、direct read 4.2 GB/s、H2D 0.39 ms/批，16.3 MB 不可能是瓶颈。
2. **已排除 DataLoader 供给不足**：单独跑 5.3 ms/批（95k/s），训练中 worker 仅 7.8 % CPU（说明预取队列是满的）。
3. **GPU 不是瓶颈**：每步纯计算 14.7 ms，实际 45 ms，利用率约 1/3。
4. **瓶颈在主进程侧每步约 30 ms 的串行开销**，且该开销**随 batch 线性增长**（46/92/182 ms ⇒ ≈90 µs/样本），因此不是“固定 kernel launch 开销”，而是每样本都要过一遍的 CPU 路径；这一点与“worker 空闲、队列已满”并不矛盾——它发生在主线程消费者端。
5. **被否定的假设**（重要，避免重复走弯路）：
   - 带权 `CrossEntropyLoss`：`bench_loss` 的 round0 全快、round1 全慢，与 criterion 种类无关 → 不是它（`bench_loss2` 里 nn 版 15.8 ms、手写版 30.4 ms，同样自相矛盾）。
   - label smoothing：无影响（15.4 ms）。
   - checkpoint I/O：`--checkpoint-every-batches 0` 与 100 无差别。
   - GPU 降频 / 节流：运行中 2782 MHz、无 throttle reason 激活。
   - `GradScaler` 的 76 次每步同步：改为 bf16 免 scaler 只降到 34.8 ms，约 10 %，在噪声范围内。
6. **台架抖动的真实幅度是 ±2×**：同一脚本同一配置在不同时间跑出 15.2 与 33.3 ms；环境为 `powersave` governor、swap 曾占用 2.9 GB。所有微基准都必须 ≥3 轮取中位数，且不能跨时段比较——第 4.1 节表格中 `bench_stage` 的非单调即由此产生，**该台架结论作废**。

### 4.4 尚未定位与下一步

- 剩余约 30 ms/步、且按样本线性增长的主进程开销，需要在**真实 `train.py` 循环内**插入分阶段计时（`next(iterator)` / H2D / forward / backward / `scaler.step` / 日志）并配合 `py-spy dump` 抓主线程栈，才能收敛。
- 在此之前不做投机性改写：唯一稳妥候选是 bf16 免 `GradScaler` + 损失张量累加，预期 ≤10 %。
- 建议把 `cross_entropy` 之外的每步 `.item()` 全部移到 epoch 末；`--checkpoint-every-batches` 提到 1000（本机默认 100 意味着每 epoch 写约 3.4 GB）。
